## Problem Statement

长期使用 Mac 的大学生独立开发者每天在代码、浏览器、文档、聊天、日历、照片和位置足迹之间切换。数据存在，但彼此分散：回顾一天需要手动翻多个应用，通常只能列出做过什么，无法可靠地回答“那天到底在推进什么”“我去了哪里”“我学了什么”“我是否真的在进行自己的目标”。

River Diary 的第一条产品闭环是：从真实数据源生成一份带证据的每日事实报告，将报告和来源存入个人事实库，再允许用户用自然语言查询和跨期比较。

长期愿景是一个跨设备、私密、可追溯的个人 OS：它不只是保存记录，而是把一个人的生活证据组织成可查询、可纠正、可比较的长期记忆。

## Demand Evidence

- 当前最强证据来自创始人自身：已经持续构建并使用 macOS 应用，并明确描述了日常替代流程。
- 现有手工流程会翻 Apple 日历、浏览器历史、终端记录、照片、备忘录、地图足迹以及微信和 QQ 聊天记录；一次回顾一天约需 15 分钟。
- 真实痛点不是找不到单条记录，而是无法将碎片组合成总结、条目和可查询的答案。
- 真实使用中的意外是：主观上以为某天效率很高，但行为证据显示刷了很久视频、真正投入工作很少；另一些长期回顾则显示自己逐渐不再在意某个人的伤害，且比一个月前更好。
- 尚未验证外部需求、付费意愿或多人持续使用。当前结论是“个人需求已被观察到，市场需求仍未验证”。

## Status Quo

现状是多个应用各自保存一部分事实：日历保存计划，浏览器保存网页，终端和编辑器保存开发痕迹，照片和地图保存地点线索，聊天工具保存交流，备忘录保存主动记录。它们没有共同的时间轴、事实层和问答入口。

用户只能手工拼接这些来源。这个过程慢、容易遗漏，也难以区分“发生过的事实”和“对这一天的解释”。因此用户能回忆片段，却无法获得带证据的个人总结。

## Target User & Narrowest Wedge

### 初始用户

长期使用 Mac 的大学生独立开发者，日常在代码、浏览器、文档和聊天之间切换，同时希望知道项目是否真的推进、学习是否持续、时间和注意力是否与目标一致。

### 第一条楔子

每天自动生成一份带证据的“我今天做了什么”报告，保存到本地数据库，并支持查询。

报告必须区分：

- **事实**：有明确来源、时间和证据的活动或事件。
- **推断**：AI 根据多个事实做出的解释，例如“投入不连续”。
- **主观感受**：用户自己写下或确认的体验，例如“今天很焦虑”。

第一版的成功不是“接入所有数据源”，而是让用户连续使用一周后，愿意相信报告、主动纠正错误，并在需要回顾时先问 River Diary，而不是手工翻多个应用。

## Constraints

- 当前只有一名真实使用者，尚无外部需求或付费证据。
- 当前代码已包含较多 macOS 采集、加密状态、SQLite/V2 数据层、AI Provider、查询和 Today/Timeline UI；后续应复用而不是另起平行系统。
- 个人数据高度敏感，原始数据、派生事实、AI 推断和云同步副本必须分层管理。
- 任何结论都可能错，尤其是地点、投入、效率和情绪；用户必须能查看来源、纠正、删除和撤回。
- 第一阶段以 macOS 为主，但数据模型、来源适配器和模型 Provider 不能把未来的手机、Windows、网页和云同步锁死。
- 用户可以提供任意兼容的大模型 API key；模型供应商不是产品事实库的唯一依赖。

## Premises

1. River Diary 解决的不是“没有数据”，而是“数据分散，无法形成可信的个人事实与解释”。
2. 第一版以 Mac 为主，先交付每日证据报告和查询，再扩展到手机、Windows、网页和云同步。
3. 长期竞争力包含三部分：数据源覆盖广度、模型可替换性、围绕来源证据建立的个人事实库；第一版先验证少量高价值来源。
4. AI 结论必须能回到来源，并且不能把推断伪装成事实。
5. 数据采集、证据 provenance、用户纠正和隐私治理比单次模型回答更值得沉淀成长期产品能力。

## Landscape Read

公开资料显示，相邻产品已经在验证几种方向：Stonekept 结合本地提取、跨设备同步、带来源的记忆问答和用户确认；LUCI 从电脑屏幕和通话中生成可查询的日常记录；Timeless AI 走跨设备的 AI self；Memoic 走云端同步、通用搜索和可导出的 Markdown。自动生活日志也已有研究路径。

因此“AI 记住我”本身不是足够差异化的定位。River Diary 更应该把差异放在跨来源证据、事实与推断分层、个人目标进展和长期自我比较上。可引用来源：Stonekept、LUCI、Timeless AI、Memoic、AutoLife 与 Mi-Memory。

## Approaches Considered

### Approach A: Mac 首发的可信日报

先用少量 Mac 数据源生成日报、保存报告、支持证据查询。优点是最快验证核心价值并复用现有代码；缺点是首批覆盖有限。

### Approach B: 个人 OS 地基

建立统一事件/证据层、数据源适配器、报告生成管线、模型无关 Provider 和可同步的数据边界，Mac 先交付一条完整闭环，其他端按适配器接入。优点是符合跨设备和任意模型的长期方向；缺点是基础设施投入更大，必须防止在连接器工程中失去用户验证。

### Approach C: 每日真相报告

围绕“我以为效率很高，但证据显示并不是”打造垂直的自我校准体验。优点是记忆点强、容易建立产品性格；缺点是容易被理解为效率监控工具，不能单独承载完整个人事实库。

## Recommended Approach

选择 **Approach B**，但用 Approach A 的闭环作为第一阶段验收标准，并吸收 Approach C 的体验核心。

第一阶段先做：

1. 统一事件和证据记录，保留来源、时间、置信度和敏感级别。
2. 为每个数据源提供明确的适配器边界，先接入已有可用的 macOS 活动、浏览/项目证据、日历/地点和手写内容路径。
3. 生成每日事实报告，事实和推断分开保存。
4. 让 AI Provider 接受任意兼容 API key，并且不把模型输出当作事实源。
5. 将日期切换放入左侧的大导航区域，Today、Timeline、Health、Footprints、Work & Learn 和 Database 都共享左侧导航选中的日期上下文。
6. 将 Today 做成当天 Dashboard：用卡片快速查看时间线摘要、去过哪里、睡眠/心情/运动、工作、学习、娱乐和目标投入，并在每张卡片上显示评分、证据覆盖和置信度。
7. 将深层内容拆成独立工作区：Health 查看睡眠/心情/运动，Footprints 查看地点/停留/推断活动并人工矫正，Work & Learn 结合项目、浏览和地点证据，Database 查看当天全部原始数据和处理状态。
8. 让 Ask 查询返回答案、来源、时间范围、置信度和纠正入口；让 Progress、Daily Review 和 Evidence Inbox 承接跨期比较、每日复盘和待确认判断。
9. 预留云同步，但第一阶段不把云端账号、跨端冲突和远程模型调用当作首发闭环的前置条件。

## Information Architecture & Navigation

上一版把 Today 当成了主要容器，导致日期切换、摘要、查询和深层数据都挤在一个页面里。新的原则是：**日期是全局上下文，Today 是一天的总览，专业问题进入独立工作区，Database 是事实底座。**

### Left navigation and date context

左侧的大导航区域同时承担“去哪里”和“看哪一天”两件事。日期控制固定放在侧栏的上部或底部，包含前一天、当前日期、后一天、回到今天以及天/周/月范围。用户切换日期后，Today、Health、Footprints、Work & Learn 和 Database 一起切换；主内容区和各子页面不再重复日期选择器。

左侧日期上下文需要始终可见，但不应该占满侧栏：当前日期用系统选中态强调，日期跳转支持键盘操作和自然语言输入；切换工作区不会丢失当前日期。

日期块采用紧凑形式：当前日期 + 上一天/下一天按钮 + “今天”入口；天/周/月范围和日期搜索放进明确的弹出菜单。侧栏不展开完整月历，避免日期控件挤压工作区导航。

### Today Dashboard

Today 不再承载所有细节，只负责让用户在十秒内看懂这一天，并能跳到证据：

- **Day Brief**：这一天的简短总结、可解释时长、证据覆盖和整体状态。
- **What I Did**：项目、学习、工作、娱乐的时间分布，点击进入 Work & Learn。
- **Where I Went**：地点和停留时长，点击进入 Footprints。
- **Health**：睡眠、心情、运动和恢复，点击进入 Health。
- **Focus & Interruptions**：投入片段、中断片段和娱乐消耗，显示事实与推断的边界。
- **Goal Check**：用户设定的目标今天是否有行为证据支持，不能只根据打开过某个应用打分。
- **Evidence Inbox**：地点、活动分类、项目归属等低置信度判断，允许用户批量确认或修改。

卡片不是装饰性 KPI。每张卡片必须有“查看证据”“纠正”“为什么这样判断”三个明确入口；评分必须显示评分依据和缺失数据，不能用一个看似精确的数字替代解释。

Today 首屏不做等权卡片墙：先显示 Day Brief，再显示 2–3 个核心卡片（优先工作/学习和足迹），其余健康、娱乐、中断和目标信息进入紧凑事实列表或可展开区域。卡片只在它本身是一个可操作入口时存在；Timeline 和 Evidence Console 承担细节和证据密度。

### Interaction state language

| 状态 | 用户看到 |
|---|---|
| 加载中 | 保留标题和布局，只显示轻量进度，不让卡片跳动 |
| 空数据 | 明确说明没有这类数据，并给出授权或手动记录入口 |
| 部分数据 | 展示已有结果，并说明缺少哪些来源 |
| 成功 | 展示观察值、证据覆盖、置信度和下一步入口 |
| AI 失败 | 保留原始事实，说明解释暂不可用，并提供重试 |
| 待确认 | 展示推断、依据和确认/修改按钮 |

### Health

Health 聚合睡眠、心情、运动和恢复，区分用户主动输入、设备测量和 AI 推断。缺失数据显示“未知”，不能按零分处理；健康结论必须避免医学诊断语气。

### Footprints

Footprints 显示地点、到达/离开时间、停留时长和推断活动。系统可以根据地点、停留、日历、浏览记录和窗口活动推断“在图书馆学习”或“在工作室开发”，但每条推断都必须允许人工矫正，并记录矫正后的来源和时间。

### Work & Learn

Work & Learn 按项目和活动类型组织“做了什么、学了什么、娱乐了多久”。项目进展不能只由打开编辑器判断，需要结合编辑/测试/文档/浏览/手写记录；足迹可以作为上下文，但不能单独证明产出。

### Database

Database 是事实底座，不是面向普通用户的技术黑盒。用户可以按日期查看当天全部原始数据、派生事件、证据关系、报告版本、模型运行状态和失败记录。原始数据默认只读，删除和重新处理必须有清晰的影响说明。

### Bold extensions

- **Daily Review**：每天晚上显示“事实、推断、未知、需要你确认”四栏，用户可以一次性校正整天。
- **Progress**：用真实行为和用户目标比较今天、上周和上月，显示证据范围和不确定性。
- **Evidence Inbox**：把低置信度的地点、活动、项目归属集中处理，纠正会反哺后续分类。
- **Life Map**：在用户主动开启位置数据后，按地点和时间回看生活轨迹，不默认生成公开地图。
- **Source Health**：显示哪些来源今天缺失、权限失效、数据延迟或只提供部分覆盖。
- **Replay / Query Lens**：对每个 AI 答案提供“事实层、推断层、原始记录层”三种视图，避免用户把语言流畅误认为事实可靠。

### Visual thesis: dashboard river + evidence console

Today 主区域先用 Dashboard 卡片回答“这一天大致发生了什么”，Timeline 再用时间作为主轴让用户沿河流展开细节。活动、地点、学习和项目推进作为节点；右侧不是装饰性 Inspector，而是证据控制台：显示当前结论使用了哪些来源、哪些是事实、哪些是推断、置信度是多少，以及用户如何纠正。

这两个特点必须同时存在：河流负责让用户看见“这一天如何流动”，控制台负责让用户知道“为什么系统这样说”。视觉应使用原生 macOS 密度、单一河流蓝强调色、系统字体和少量等宽元数据；避免 SaaS 仪表盘、大标题、泛化聊天界面、渐变和过度圆角卡片。

## User Journey and Emotional Arc

| 步骤 | 用户动作 | 用户感受 | 设计支持 |
|---|---|---|---|
| 1 | 从左侧日期块打开今天 | 想快速定位 | 日期上下文固定，Today 首屏先显示 Day Brief |
| 2 | 扫描 Dashboard | 开始理解这一天 | 先事实摘要，再核心卡片，避免先看总分 |
| 3 | 发现主观印象与行为证据不一致 | 意外，可能不舒服 | 事实/推断分层，不使用道德化措辞 |
| 4 | 打开证据控制台 | 想验证系统有没有说错 | 显示来源、覆盖、置信度、缺失项 |
| 5 | 确认或修改判断 | 重新拥有解释权 | Evidence Inbox 支持确认、修改、撤销 |
| 6 | 回到 Timeline 或 Progress | 对自己更清楚 | 回放上下文，长期比较保留证据范围 |

时间尺度：前 5 秒知道今天发生了什么；前 5 分钟完成一次回顾或纠正；持续数月后能看到变化，但系统不替用户定义“变好”。

## Accepted Scope Expansions

- **Evidence Inbox**：集中处理低置信度地点、活动和项目归属，并让修正反哺后续分类。
- **Goals**：用用户定义的目标作为行为比较参照，不把模型生成的总分当成自我评价。
- **Daily Review**：把事实、推断、未知和需要确认的内容分开，支持生成前后的确认与版本化。
- **Source Health**：展示数据源权限、覆盖区间、失败和缺失，让“未知”不会被误解为“零”。
- **Progress**：提供跨日、周、月的目标与行为比较，并保留证据范围和覆盖说明。
- **Encrypted Sync Contract**：当前确定跨设备事实协议、模型无关 Provider、加密同步、导出、删除、恢复和冲突边界；真实云服务分阶段实现。
- **Replay / Query Lens**：查询结果提供答案层、证据层和时间回放层。
- **Life Map**：用户主动开启位置后，用地点、停留和活动上下文支持空间维度的个人回顾。

## Open Questions

- 第一批高价值数据源的精确组合是什么：应用/窗口活动、浏览历史、日历、地点、照片、聊天摘要、终端和编辑器活动应如何排序？
- Today Dashboard 首发保留哪些卡片，哪些只在对应工作区显示？
- 左侧日期范围切换如何影响跨日数据：跨午夜活动、睡眠和跨日地点如何归属？
- “我在推进 River 项目”如何从打开应用升级为有证据的项目进展判断？
- 地点、聊天和窗口标题的隐私授权、脱敏、保留期和删除语义如何设计？
- 每日报告何时生成、生成失败如何重试、用户如何知道报告不完整？
- 云同步是端到端加密的个人仓库，还是只同步派生报告？用户是否能完全导出和删除？
- 第一批外部用户是 Mac 重度开发者、大学生，还是两者交集？
- 付费点是云同步、跨设备、更多数据源、模型代理，还是长期报告与对比能力？

## Success Criteria

### 第一阶段产品指标

- 连续 7 天生成日报，至少 6 天有可解释的证据覆盖。
- 每份日报将事实、推断和主观感受分开，并能展开来源。
- 对“哪天去过图书馆”“哪天推进了 River 项目”等问题，答案能返回日期、来源和置信度。
- 用户可以在左侧大导航中切换日期，并让 Today、Health、Footprints、Work & Learn 和 Database 同步切换。
- Today Dashboard 的每张卡片都能在一次点击内进入证据详情，而不需要重新搜索。
- 足迹、活动归属和项目进展判断都支持人工矫正，并记录矫正前后的依据。
- 用户能在 30 秒内发现并纠正一个错误判断，纠正后不会被再次当作事实复用。
- 至少 3 名外部 Mac 重度用户连续使用 7 天；记录他们每天打开日报、查询、纠正和放弃的原因。
- 外部测试中，用户愿意用 River Diary 替代一次手工翻查多个应用的回顾过程。

### 长期产品指标

- 新数据源通过适配器加入，不重写事实库和报告 UI。
- 更换兼容模型 key 不影响已有事实、证据和历史报告。
- 云同步可在不让服务端读取明文个人事实的前提下工作。

## Engineering Review Decisions

- Phase 1 is the current implementation boundary; later workspaces remain architecture constraints, not simultaneous code scope.
- SQLite access moves behind a `DatabaseActor` and returns immutable snapshots to SwiftUI.
- V2 uses versioned migrations, backup/verification, legacy-read fallback, and rollback records before shadow projections become authoritative.
- Database introspection uses an allowlisted schema registry; arbitrary table-name SQL interpolation is removed.
- DateContext, Dashboard state, report state, and correction state are pure/testable models backed by V2 integration tests and a real macOS smoke checklist.
- Raw event browsing uses time cursors/pagination and list/detail projections instead of loading unbounded payloads.

Engineering test plan: `~/.gstack/projects/qingning0524-river-diary/fa1lingdown-codex-ui-redesign-eng-review-test-plan-20260921.md`.

## Design Review Decisions

- Sidebar date context is compact: current date, previous/next day, Today, and a range popover; it does not expand into a full calendar by default.
- All cards and workspaces share loading, empty, partial, success, AI-failed, needs-review, and stale state language.
- The user journey is calm truth: orient → understand → notice surprise → inspect evidence → correct → reflect.
- Today uses Day Brief + 2–3 core cards + compact facts; Timeline and Evidence Console carry detail instead of an equal-weight card mosaic.
- `DESIGN.md` is the source of truth for Phase 1 tokens and components.
- Mac windows have wide, standard, and narrow layouts with the Evidence Console becoming a drawer/sheet as space decreases.
- Phase 1 surfaces migrate to the new token system; untouched legacy screens keep existing tokens until their own redesign.
