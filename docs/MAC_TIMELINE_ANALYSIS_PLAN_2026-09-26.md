# macOS 时间线分析逻辑规划

> 后续产品方向（2026-09-26）：[时间线数据列表 UI 重构方案](MAC_TIMELINE_LIST_UI_REDESIGN_2026-09-26.md)已落地为「启用自动整理后生成 AI 时间段，原始记录可核对，用户少操作」。本文关于固定五列列表的细节描述的是 `原始记录` 视图；其中“用户显式请求时才生成 AI”的旧流程已由设置开关控制的自动整理取代。

日期：2026-09-26  
状态：已实现，2026-09-26

## 目标

让用户在一天结束时回答三个问题：**记录到了什么、这些记录能支持什么判断、哪里仍然未知**。时间线继续按时刻展示证据；Today 用少量有依据的句子概括这一天；复盘与可选 AI 使用同一套日内事实。应用使用时长是观察值，不自动等于项目进展、专注质量、地点或情绪原因。

首轮沿用现有应用切换、窗口标题、快记、日记和项目管道数据，不增加屏幕录制。分析结果优先在本机确定性生成；AI 只解释经过整理的事实，继续遵守现有显式连接、发送范围和窗口标题开关。

## 已有基础与需要收敛的地方

| 现状 | 依据 | 规划处理 |
|---|---|---|
| 时间线会裁剪跨日片段、去掉重叠时长，保留逐条 `items`，只在显示层折叠短切换 | `ActivityTimeline.swift` | 直接复用，分析不得读取 `foldedItems` 计算时长或证据数 |
| Today 的本地日报按片段数量挑主要应用，按活动**开始时刻**归入凌晨/上午等时段 | `LocalDayReport.swift` | 改为按实际时长选主项；跨时段活动按边界分配时长 |
| 时间线与融合统计分别计算实时总量；后者直接累加 `liveSessions`，而时间线做重叠归一 | `ActivityTimeline.swift`、`ActivityFusionEngine.swift` | 统一实时计时输入，项目管道的日汇总另列来源，不与实时片段相加 |
| V2 `Episode` 按同应用与同类别归组，时间线活动块按同类别归组 | `ActivityV2Projection.swift`、`ActivityTimeline.swift` | 明确两者语义并保留到原始片段的关联；跨页面跳转以原始证据引用定位，不依赖两个分组边界恰好相同 |
| 人工类别映射在读取时生效；地点页和学习工作页构建时间线时未传入 `timelineAnnotations` | `ActivityStore.swift`、`FootprintsWorkspaceView.swift`、`WorkLearnWorkspaceView.swift` | 让这些页面消费同一份带人工修正的快照，地点标注才能出现在地点页 |
| 时间线覆盖说明和日带的位置/拖动换算都使用固定 `86_400` 秒 | `TimelineWorkspaceView.swift`、`TimelineRibbon.swift` | 改为当前日的 `Calendar.dateInterval(of: .day)` 长度；夏令时跳时/重时需有明确的本地时刻提示 |
| 日级 `ActivityConfidenceEngine` 评分描述数据覆盖与双源一致性，V2 `Episode` 则按首段有无标题给固定的 85/65 分 | `ActivityConfidenceEngine.swift`、`ActivityV2Projection.swift` | 明确“数据覆盖”和“单条解释可信度”是两个字段；固定分数不充当完成事项的可信度 |
| AI 结果属于 `AnalysisRun`，证据引用可解析并按本机白名单筛除 | `AnalysisRun.swift`、`EvidenceReference.swift` | 继续让模型输出与事实层隔离，逐条结论引用可打开的证据 |

现有产品约束保持有效：短切换是中性结构，不等于分心；空档代表没有记录，不等于休息；待确认队列仍只收至少 20 分钟且没有说明的活动。它们已经写入 `DESIGN.md`，本次不重新调阈值。

## 分析契约

新增一个不写回原始数据的 `TimelineAnalysisSnapshot`（名称可在实现时调整）。它从选定日期与现有数据源生成：

1. **观察事实**：日期内的非重叠前台区间、实际计时时长、应用与类别、采集到的窗口标题、快记时刻、人工标注、每条事实的 `EvidenceReference`。项目管道只有日级汇总时，只能作为日级事实，不能放到虚构的时刻。
2. **覆盖与冲突**：当天实际日长、已记录区间、未知区间、采集/标题权限状态，以及实时与项目管道汇总是否冲突。覆盖率只描述数据覆盖，不作为用户效率或单条结论的可信度。未经校准的单条判断不显示 0–100 分。
3. **日内线索**：按时长而非片段数排序的应用/类别分布、确实观察到的长活动块、人工留下的重点、短切换的结构。每条线索包含时间范围、事实/推断/用户表述类型、证据引用及一句“为何这样说”。
4. **待解释事项**：只复用当前 `needsReview` 判定。缺标题但不足 20 分钟、空档和折叠碎片带不新增确认任务。

展示文字的优先级：用户的标题与活动标注 → 已采集窗口标题 → 应用及类别。用户指定的应用类别覆盖自动分类，但原始片段不改写。没有可支撑的项目归属、完成事项、地点或情绪原因时，输出“未知”或只陈述应用使用；不填充一个看似合理的故事。

## 计算流程

```text
原始实时片段 + 当天快记 + 日记/人工标注 + 日级导入汇总
  → 按本地日界裁剪、过滤不可记录进程、重叠去重
  → 构造 ActivityTimeline.items（完整证据）
  → TimelineAnalysisSnapshot（事实、覆盖、线索、待解释）
  → Today 简报 / Timeline 证据详情 / 复盘与学习工作页
  → 用户显式请求时，生成受隐私开关约束的 AI 事实输入
```

- 计时只用规范化后的有效区间；活动块的 `span` 与实际前台 `duration` 分别保留，前者不能冒充后者。空档可显示，但不计入“未工作”“休息”或专注比例。
- 同时有实时与项目管道数据时，各自标明口径。导入的日总量没有逐分钟时间戳，不能拿来填时间线空档；差异超过现有阈值时给出冲突说明。
- 每条日内线索保留原始引用。跨页面打开线索先解析 `raw:` / `capture:` / `episode:` 等现有引用，再定位对应时间线行；折叠状态不得隐藏被定位的成员。
- 本地日报优先挑人工记述和时长足够、有来源的活动，最多展示三条，并避免三个同义的“使用某应用”句子。只有应用名时使用“使用了……”，不写“完成了……”。
- AI 输入使用这份快照中的有界事实清单与当前范围的统计，避免直接依赖任意截断的原始片段列表。发送窗口标题前检查已有独立开关；输出仍存 `AnalysisRun`，证据引用经 `EvidenceReference.allowedSet` 核对。没有依据的解释不能进入事实库。

## 落地顺序

### 阶段 1：统一事实口径

在 `ActivityTimeline.swift` 提取可复用的日内规范化结果，供 `ActivityFusionEngine.swift` 和新分析器消费；沿用 `ActivityStore.swift` 现有的类别映射缓存清理，并确认其他快照输入变化时缓存也会失效。修正时间线覆盖说明与 `RiverDayRibbon` 的日长换算；普通日维持 00–24 标尺，夏令时变更日说明跳过/重复的本地小时。先让同一天的时间线、Today 和统计页对“实时已记录时长”给出同一数值。此阶段不改数据库结构。

### 阶段 2：本地分析与人工修正

新增独立的日内分析器及小型值模型，把 `LocalDayReportBuilder` 的主要应用/分时逻辑迁到该快照。Today 展示最多三条带依据的重点；Timeline 保持现有有序行，Inspector 解释依据和未知。`FootprintsWorkspaceView`、`WorkLearnWorkspaceView` 使用带 `timelineAnnotations` 的结果，人工地点/活动标签在保存后立即更新相关页面。

### 阶段 3：AI 与跨期复用

让 `AIAssistantStore` 的每日总结先读取确定性事实清单，再选取原始记录作补充；每条 AI 结论区分观察与推断，保留可核对引用。`LocalReview` 的 7/30 天比较从同一日级快照聚合，缺少记录的日子显示为缺数据，不当作零。后续只有在项目、浏览或日历证据足以支撑时，才加入“项目推进”推断。

## 验收样例

| 输入 | 应看到 |
|---|---|
| 10:00–10:30 与 10:20–10:40 两段重叠 | 实时已记录 40 分钟，所有页面一致；两条原始依据仍可查 |
| 23:50–次日 00:10 一段活动 | 两天各计 10 分钟，证据仍指向来源；夏令时日按实际日长计算未知区间 |
| 只有“Chrome 45 分钟”，没有标题或人工说明 | 陈述 Chrome 的观察值，不说完成了工作，也不填项目名；符合现有规则时进入待确认 |
| 用户给活动写标题或地点，或在设置里改应用类别 | Today/时间线/地点/学习工作页刷新；原始采集内容不改 |
| 项目管道 4 小时、实时记录 3 小时 | 分别标来源及冲突，不显示 7 小时 |
| 一小时里多次短切换 | 可展开看到全部原始项；用结构描述组合工作/短切换，不推断“分心” |
| 无采集、权限关闭或补写旧日快记 | 说明未知与数据来源；补写快记不伪造发生时刻 |
| AI 给出不存在的证据 ID 或无依据的“完成事项” | 引用被拒绝或结论被降级/舍弃；事实库不新增该断言 |

实现阶段优先扩展现有 `ActivityTimelineTests`、`ActivityFusionTests`、`LocalDayReportTests` 和 `EvidenceReferenceTests` 的行为样例；这些是边界与来源校验，不以界面文案逐字匹配替代逻辑检查。完成后以一周真实使用观察：每日能否在十秒内读出有依据的重点、一次错误能否找到并修正、修正后所有页面是否一致。

## UI 设计方案：可核对、可修正的一日证据

### 产品辨识度

河流的时间线是一份**可改写的个人证据报告**。固定在页头的 24 小时时间带让用户看到“哪段有记录”；两行证据列表让用户读出“记录到了什么”；详情栏解释“为什么这样说”并接收人工修正。用户写下的一句话与自动采集并列呈现，但始终标明是用户记述。灰色留白明确写“未记录”，不暗示休息、低效或空白人生。

视觉上沿用已批准的 `DESIGN.md`：暖纸色画布、实体浅色面板、单一克制的强调色、清晰的发丝线和固定列宽。分析状态靠文字与节点形状表达，不使用红绿生产力评分、类别彩虹、装饰性流水动画。新增设计须复用 `AppTheme`、`AppTypography`、`AppSpacing`、`RiverPanel` 和 `TimelineRowMetrics`，不另建一套卡片样式。

### 三个页面的职责与低保真结构

```text
Today：十秒读懂一天
  日期 + 主动作
  现有四项概览 + 24 小时时间带
  「今天发生了什么」：一句事实总览 + 最多三条可点开的重点
      09:20–10:40  组合使用 Xcode 与终端     [观察] [查看依据]
      14:10         「在图书馆复习」           [我写的] [查看原文]
      16:00–16:35  Chrome 的用途还不清楚     [待解释] [写一句]
  其余目标、健康、地点和待确认项保持原有入口

Timeline：沿时间核对过程
  固定页头：日期 + 24 小时时间带（悬停读时刻，拖动定位）
  原有四项概览 → 收起的日记 → 筛选 → 两行一条的证据列表
  选中节点后，右侧同一栏由证据控制台切换为详情

Inspector：理解并纠正一条判断
  类型与时间 → 这条记录说了什么 → 为什么这样说
  原始片段 / 快记 / 人工标注 → 依据完整度与缺失项
  编辑标题、地点、活动标签或确认状态 → 保存后返回原行
```

上面的句子只是交互示例，不代表应用可从“打开 Xcode/Chrome”自动得知具体工作内容。Today 的重点行使用同一份 `TimelineAnalysisSnapshot`，不从另一套文案规则重新计算。时间线仍以有序行作为主体，不在列表前再加入第二份“日报卡片”。

重点行采用紧凑的时间列、正文和文字型类型标记，来源与动作只占一处次要位置；不做三张大卡或每行多个彩色徽章。只有确实存在值得处理的未知事项时，才占用一条「待解释」重点；正常的一天不为了凑满三个位置而制造问题。

### 关键组件的改动

| 现有组件 | UI 方案 | 约束 |
|---|---|---|
| `TodayDashboardView.dayBrief` | 把纯文本重点改为最多三条可操作的“时间 + 结论 + 来源”行；每条有观察/用户记述/待解释文字标签和明确的「查看依据」或「写一句」动作 | 不把同一应用的三个片段写成三条相似结论；没有依据时显示缺失原因 |
| `TodayDashboardView.glanceHero` | 保留现有时间带与概览位置；将“证据质量 92%”与单条判断分开解释，必要时用“来源状态/已记录时长”替代容易被当作效率分的百分数 | 未记录时长不按零计；工作类别缺失时不把“专注 0”解释为没有专注 |
| `RiverDayRibbon` | 继续用实心片段、人工快记标记与中性留白表现一天；悬停留白显示“这一刻没有实时记录” | 点击首条之前或末条之后的留白，不跳到最近的活动并假装那里有证据；真正的中段空档定位到空档行；夏令时日按实际日界定位并标明异常小时 |
| `RiverTimelineView` | 维持固定五列、每行两行和现有碎片带展开；被 Today 重点定位的成员自动展开、滚入视口并高亮 | 筛选或展开不改变统计和证据集合；证据类型不靠颜色单独区分 |
| `InspectorPanel` | 在现有“摘要/依据/整理”之间加入简短「为什么这样说」；把当前仅按标题数量得出的“高/中/低可信度”改成可读的「依据完整度：仅应用 / 应用与标题 / 用户补充」及缺失项 | 依据完整度描述数据细度，不代表完成事项、地点或意图的真实性；碎片带仍不可直接编辑 |
| `EvidenceConsoleView` | 保留“正在记录 / 需要你确认 / 信任”三块；在“信任”中提供本日来源和缺失权限入口 | 队列仍按现有 20 分钟规则，空档与短切换不制造待办 |

### 一条完整交互链

1. 用户在 Today 点一条重点的「查看依据」，日期上下文保持不变，进入该时刻的 Timeline。若目标属于碎片带，先展开并定位真实成员；右侧打开对应详情。
2. 详情按“观察到的事实 → 系统的解释 → 原始依据 → 我的修正”阅读。窗口标题缺失就写明只知道应用名；导入汇总没有时刻就只出现在日级说明，不伪装成时间线节点。
3. 用户写下标题或地点并保存。保存成功后，Today 重点、时间线行、地点页/学习工作页和待确认状态同步更新；保存失败保留输入与错误提示，不显示已完成。
4. 用户返回 Today 时，同一条重点保留时间与证据入口。AI 版本若存在，明确标“AI 解释”，可以查看其引用，不覆盖用户自己的表述或本机事实。

### 状态与响应式规则

| 状态 | 界面表达 |
|---|---|
| 没有实时记录，但有日记或补写快记 | 展示用户文字，并说明没有可定位的活动时刻；补写内容留在“补记”区域 |
| 只有应用名，没有窗口标题 | 行中只写应用与时长；在详情与权限提示中说明判断边界 |
| 来源冲突或覆盖不足 | Today 给简短来源说明，Inspector 列出差异；留白保留中性色，不出现评价性红色 |
| AI 未连接、请求失败或尚未运行 | 本地事实和时间线照常可读；分别提供连接、重试或手动生成入口 |
| 正在记录的今天 | 时间带保留“现在”刻度；尚未结束的片段标记为进行中，摘要不把它写成已完成 |

版心继续使用 `AppLayout.contentMaxWidth`。右侧证据栏沿用 `RiverShell` 当前的响应式断点；窄窗以浮层打开详情，关闭后焦点回原记录。960、1280、1440pt 三档都要能读完整时间、标题、来源与动作；新增信息在内容列换行，不增加第六个固定列。支持键盘打开重点、定位到行、编辑与 Esc 返回；悬停提示有键盘可达的同等入口，并遵守高对比度、无颜色区分和减少动态效果设置。

### UI 落地顺序

1. 随事实口径阶段，先统一 Today 与 Timeline 的时长、来源和未知文案，校正“证据质量/可信度”的解释；保留当前布局与尺寸。
2. 随本地分析阶段，改 `TodayDashboardView.dayBrief` 的三条可点开重点，补 `InspectorPanel` 的「为什么这样说」，打通重点定位、碎片带展开、人工修正后的跨页面刷新，并修正日带留白定位。
3. 随 AI 与跨期阶段，给 AI 解释独立标签和可核对引用；复盘只展示有样本支撑的跨日线索。每阶段在真实窗口核对之后再进入下一阶段，避免逻辑、导航和视觉同时大改。

### UI 验收

- 第一次进入 Today，十秒内能指出一条有依据的重点、查看来源的入口；若有未知或缺失，也能看出它在哪里。
- 从一条 Today 重点到原始依据最多两次操作；日期、选中态和键盘焦点可预测地保持。
- 人工修正保存后，相关页面立即一致；失败时输入不丢。长中文标题、空数据、部分权限与数百节点日均可读。
- 960/1280/1440pt、浅/深色和标准/紧凑密度下，不出现横向滚动、裁切或把“未知”仅用颜色表达。
- 视觉复核以真实 macOS 窗口为准；如果改动日带、节点或脊柱几何，沿用现有像素级渲染检查，不用文案快照代替。
